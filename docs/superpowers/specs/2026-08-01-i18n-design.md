# Multi-language pages (es, hi) - design spec (2026-08-01, rev2 after cold Fable review)

## Goal

Serve Spanish and Hindi versions of all five platform pages under /es/ and /hi/
path prefixes with a full hreflang cluster, as the first two locales of a
framework where adding a language is copy work, not code work. Rationale from
traffic data: ~30% of downloads are Spanish-speaking countries (es is the
evidence-backed locale). hi is an OWNER DECISION made with the data stated
plainly: India is 1.0% of downloads today (30d window, 2026-07-29), Indian
downloader queries are predominantly Latin-script English/Hinglish which the
en pages already target, and the hi pages bet on the Devanagari segment of
the world's largest Instagram market. Expectation set accordingly; pt-BR is
the likely higher-yield third locale when its traffic justifies it.

## URL and hreflang model (pre-committed in the SEO spec)

- English stays at the root (x-default and en). Locales at /es/<same-slug> and
  /hi/<same-slug>. Slugs stay English (no translated slugs: redirect and
  duplicate-content complexity for marginal gain).
- HOME PAGE (empty slug), pinned: the Twitter page's locale form is /es/ and
  /hi/ (clean form with trailing slash; Starlette's default redirect handles
  /es -> /es/), alias /es/index.html and /hi/index.html. Routes for all locale
  paths are declared BEFORE the static mount, and a test pins that the raw
  mount never serves a locale shell with an unconsumed <!--ADS--> marker.
- Every page in a cluster (en root, es, hi) carries the SAME set of hreflang
  link tags: en + es + hi + x-default (pointing at the en root page),
  all absolute URLs, self-inclusive per Google spec. Shell link tags are the
  ONLY hreflang source: the sitemap carries NO xhtml alternates (one
  hand-maintained artifact, not two drifting ones); the cluster test parses
  the 15 shells.
- Canonicals: each locale page is self-canonical.
- html lang="es" / lang="hi" per shell; og:locale es_LA (Facebook's LatAm
  Spanish code, matching the copy register; NOT es_ES) / hi_IN, plus
  og:locale:alternate tags listing the other two locales on every page
  (closes the deferred thread from the SEO spec).
- sitemap.xml: 15 plain URLs with lastmod (en pages' lastmod bumps to this
  release date: they gain hreflang tags and the switcher, a real content
  change under the hand-maintained-lastmod rule).

## Architecture

### Shells (10 new static files)

frontend/es/<page>.html and frontend/hi/<page>.html for all five pages,
translated COPIES of the English shells: meta title/description, OG/twitter
tags, JSON-LD FAQ (subset invariant holds per locale), static hero snapshot
(translated h1/sub/placeholder/button), how-it-works steps, visible FAQ,
footer (translated platform anchor texts linking WITHIN the locale, plus a
small language switcher nav with AUTONYM labels: "English", "Espanol" with
the accent, and Hindi written in Devanagari script, each linking to the same
page in its locale, static and crawlable, present on all 15 shells). Exactly one <!--ADS--> marker each
(ads earn on locale pages too). OG images: reuse existing og-*.png (brand
graphics, text is minimal; localized OG images are out of scope v1).

### React (shared apps, string tables)

- New frontend/src/locales/ module: strings.en.ts (extracted current copy),
  strings.es.ts, strings.hi.ts. One typed Strings shape per platform page
  (hero words, lede, placeholder, aria, chips, notes, nav labels, error-region
  labels: everything user-visible in the app).
- Strings reach the apps by PROP THREADING from the entry file
  (`<InstagramApp strings={esInstagram} />` with an English default), MANDATED
  (cold-review Blocker): a module-level setStrings() breaks against import
  hoisting (module-scope constants capture defaults before the entry runs)
  and against the 15-combo test plan (module state leaks between renders in
  one jsdom process). Companion rule: NO component may read strings at module
  scope; PlatformLinks' module-level PLATFORMS array moves inside the
  component so labels AND hrefs are locale-correct.
- 10 new Vite entries (es/hi per platform) reusing the same apps:
  frontend/src/entries/<locale>-<platform>.tsx. Vite MPA input map grows to 16.
- Strings inventory is EXHAUSTIVE, not illustrative: every user-visible
  literal in PasteInput/PreviewCard/PhotoGrid/QualityButton/SkeletonCard/
  ThemeToggle (button states like "Fetch"/"Saved"/"retry", "Save all",
  "Sound"/"Sound saved", "Video N" headings, aria-labels incl "Save photo N"),
  the HowToVisual SVG <text> elements and figcaptions on every platform
  (user-visible English otherwise), and CLIENT-MINTED error strings
  (useResolve's network-error message, api.ts fallback messages). ONLY the
  backend `body.message` passthrough stays English v1 (a backend errors-i18n
  task, out of scope, noted honestly). Acceptance: a grep sweep for remaining
  Latin UI literals rendered on es/hi pages.
- PlatformLinks and footer hrefs become locale-aware (prefix from the strings
  table). Analytics beacons unchanged (platform values stay canonical
  English). MEASUREMENT: locale performance is read from Search Console
  per-URL impressions/clicks (the owner's pending GSC setup is the
  prerequisite; admin country stats remain a proxy). No new analytics fields
  in this spec.
- Typography: hi pages accept the OS Devanagari fallback v1 (Onest has no
  Devanagari; system fonts on Android/iOS/Windows are high quality). The
  live gate includes a hi glyph/clipping check in the hero clamp sizing.
  Verify at build time that the Onest subset's unicode-range covers Spanish
  punctuation (inverted marks, accents); extend the subset if not.

### Backend

- main.py: the per-page route pairs generalize to a loop over
  PUBLIC_PAGES x LOCALES serving renderer.render(f"{prefix}{page}.html")
  for /es/... and /hi/... (clean + .html forms, incl the /es/ and /hi/ home
  forms), still before the static mount, still through PageRenderer (ads +
  maintenance behavior come free). Loop body binds the filename per
  iteration (default-arg or factory: the classic closure-capture bug is
  called out here so no route serves the last page). STATIC_DIR ships es/
  and hi/ subdirectories via the Vite build output (verified: nested HTML
  inputs keep their root-relative paths in dist, asset refs are absolute
  /assets/...).
- robots.txt/sitemap.xml unchanged in location; sitemap grows to 15 plain
  entries with lastmod (NO xhtml alternates: shells are the only hreflang
  source).

### Translations

- All es/hi strings are authored in a committed reference doc
  (docs/superpowers/specs/2026-08-01-i18n-translations.md) BEFORE the plan, so
  implementer tasks copy verbatim and reviews check character-fidelity, same
  as the FAQ tasks did. Register: es = neutral Latin American Spanish (the
  traffic is MX/AR/CL/CO-heavy, tu-form, no vosotros); hi = standard Hindi in
  Devanagari, common loanwords kept in Latin script where natural (video,
  reel, download button labels may stay recognizable loanwords per common
  Indian app convention).
- Honesty constraints carry over exactly (no watermark claims outside tiktok,
  hedged legality, Files-app iOS wording, "one real click" register).

## Testing

- Existing parity/footer/faq test suites generalize: heroSnapshot,
  footerLinks, faqJsonLd iterate (shell, app, strings) triples across 15
  pages. h1-once, marker-once, noindex-absent greps extend to locale shells.
- New hreflang test: every page's alternates form a complete, consistent,
  absolute-URL cluster (parse all 15 shells; the 3 per-slug clusters must
  agree; x-default = en root).
- Backend: locale routes 200 through the renderer, blocked by maintenance,
  ad-marker consumed; PUBLIC_PATHS grows to 30 ROWS (15 pages x clean+.html;
  the tmp_path test helper gains mkdir for es/ and hi/). Raw-mount
  marker-leak canary for /es/index.html.
- Language switcher: static autonym links present on all 15 shells (test).
- Live gate: browser check of es and hi pages (desktop+mobile), resolve flow
  works on a locale page end to end, prod curls after deploy.

## Out of scope

Backend error message translation, localized OG images, translated slugs,
locale auto-redirect by Accept-Language (deliberately NOT done: Google
recommends against automatic redirects; the switcher plus hreflang handle
discovery), RTL locales, additional languages beyond es/hi (framework makes
them copy drops later), localized maintenance page (English for all locales
v1), analytics locale field (GSC is the measurement).

## Risks

- Translation register quality: mitigated by the committed reference doc and
  cold review of the actual strings; the owner can veto any string.
- Copy drift across 3 locales x 5 pages: the generalized parity tests are the
  guard, same mechanism as the SEO branch.
- Thin-content risk of translated pages: pages are full translations of
  substantive pages (not machine-stub doorways), interlinked and
  hreflang-clustered: the accepted, standard pattern.
