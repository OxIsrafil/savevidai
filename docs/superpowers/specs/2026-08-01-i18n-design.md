# Multi-language pages (es, hi) - design spec (2026-08-01, draft for cold review)

## Goal

Serve Spanish and Hindi versions of all five platform pages under /es/ and /hi/
path prefixes with a full hreflang cluster, as the first two locales of a
framework where adding a language is copy work, not code work. Rationale from
traffic data: ~30% of downloads are Spanish-speaking countries; India is a
high-volume Instagram market where Hindi pages capture Devanagari queries (the
English pages already serve India's dominant English-query behavior; the spec
does NOT claim Hindi replaces that).

## URL and hreflang model (pre-committed in the SEO spec)

- English stays at the root (x-default and en). Locales at /es/<same-slug> and
  /hi/<same-slug>. Slugs stay English (no translated slugs: redirect and
  duplicate-content complexity for marginal gain).
- Every page in a cluster (en root, es, hi) carries the SAME set of hreflang
  link tags: en + es + hi + x-default (pointing at the en root page),
  all absolute URLs, self-inclusive per Google spec.
- Canonicals: each locale page is self-canonical.
- html lang="es" / lang="hi" per shell; og:locale es_ES / hi_IN.
- sitemap.xml: 15 URLs, each with xhtml:link hreflang alternates (the sitemap
  namespace gains xhtml). lastmod per URL.

## Architecture

### Shells (10 new static files)

frontend/es/<page>.html and frontend/hi/<page>.html for all five pages,
translated COPIES of the English shells: meta title/description, OG/twitter
tags, JSON-LD FAQ (subset invariant holds per locale), static hero snapshot
(translated h1/sub/placeholder/button), how-it-works steps, visible FAQ,
footer (translated platform anchor texts linking WITHIN the locale, plus a
small language switcher nav: English | Espanol | Hindi linking to the same
page in each locale, static and crawlable). Exactly one <!--ADS--> marker each
(ads earn on locale pages too). OG images: reuse existing og-*.png (brand
graphics, text is minimal; localized OG images are out of scope v1).

### React (shared apps, string tables)

- New frontend/src/locales/ module: strings.en.ts (extracted current copy),
  strings.es.ts, strings.hi.ts. One typed Strings shape per platform page
  (hero words, lede, placeholder, aria, chips, notes, nav labels, error-region
  labels: everything user-visible in the app).
- The five apps take strings via a module-level provider set by the entry file
  (no context library; a simple `setStrings()` + typed getter, or a prop
  threaded from the entry: implementer picks the smaller diff, uniformly).
- 10 new Vite entries (es/hi per platform) reusing the same apps:
  frontend/src/entries/<locale>-<platform>.tsx. Vite MPA input map grows to 16.
- PasteInput/PreviewCard/PhotoGrid/QualityButton: user-visible literals move to
  the strings table (labels like "Fetch", "Save all", error region text).
  Backend error MESSAGES stay English v1 (they come from the API; translating
  them is a backend errors-i18n task explicitly out of scope, noted honestly).
- PlatformLinks and footer hrefs become locale-aware (prefix from the strings
  table). Analytics beacons unchanged (platform values stay canonical English).

### Backend

- main.py: the per-page route pairs generalize to a loop over
  PUBLIC_PAGES x LOCALES serving renderer.render(f"{prefix}{page}.html")
  for /es/... and /hi/... (clean + .html forms), still before the static
  mount, still through PageRenderer (ads + maintenance behavior come free).
  STATIC_DIR ships the es/ and hi/ subdirectories via the Vite build output.
- robots.txt/sitemap.xml unchanged in location; sitemap grows to 15 entries
  with hreflang alternates.

### Translations

- All es/hi strings are authored in a committed reference doc
  (docs/superpowers/specs/2026-08-01-i18n-translations.md) BEFORE the plan, so
  implementer tasks copy verbatim and reviews check character-fidelity, same
  as the FAQ tasks did. Register: es = neutral Latin American Spanish (the
  traffic is MX/AR/CL/CO-heavy, tu-form, no vosotros); hi = standard Hindi in
  Devanagari, common loanwords kept in Latin script where natural (video,
  reel, download button labels may stay recognizable loanwords per common
  Indian app convention).
- Honesty constraints carry over exactly (no watermark claims outside tiktok,
  hedged legality, Files-app iOS wording, "one real click" register).

## Testing

- Existing parity/footer/faq test suites generalize: heroSnapshot,
  footerLinks, faqJsonLd iterate (shell, app, strings) triples across 15
  pages. h1-once, marker-once, noindex-absent greps extend to locale shells.
- New hreflang test: every page's alternates form a complete, consistent,
  absolute-URL cluster (parse all 15 shells; the 3 per-slug clusters must
  agree; x-default = en root).
- Backend: locale routes 200 through the renderer, blocked by maintenance,
  ad-marker consumed; PUBLIC_PATHS table grows to 15 (ads/maintenance
  coverage comes free from the existing loops).
- Language switcher: static links present on all 15 shells (test).
- Live gate: browser check of es and hi pages (desktop+mobile), resolve flow
  works on a locale page end to end, prod curls after deploy.

## Out of scope

Backend error message translation, localized OG images, translated slugs,
locale auto-redirect by Accept-Language (deliberately NOT done: Google
recommends against automatic redirects; the switcher plus hreflang handle
discovery), RTL locales, additional languages beyond es/hi (framework makes
them copy drops later).

## Risks

- Translation register quality: mitigated by the committed reference doc and
  cold review of the actual strings; the owner can veto any string.
- Copy drift across 3 locales x 5 pages: the generalized parity tests are the
  guard, same mechanism as the SEO branch.
- Thin-content risk of translated pages: pages are full translations of
  substantive pages (not machine-stub doorways), interlinked and
  hreflang-clustered: the accepted, standard pattern.
